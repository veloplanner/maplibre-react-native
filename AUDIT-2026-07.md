# Performance, Battery & Maintainability Audit — July 2026

Audited at commit `69113243` (branch `fix/android-map-stability`). Static source review of all
three layers; findings marked **Confirmed** were verified in source, **Suspected** need runtime
confirmation. Severity reflects real-world impact for a typical map app.

Path shorthand:

- **Android** = `package/android/src/main/java/org/maplibre/reactnative/`
- **iOS** = `package/ios/`
- **JS** = `package/src/`

## 1. Executive summary

The codebase is healthy overall: new-architecture-only on every layer (Fabric + TurboModules +
codegen, no legacy bridge), location tracking is opt-in from JS, TypeScript config is very strict,
and CI is strong (type-check, JS + Kotlin lint, unit tests, native example builds, semantic-release
with npm provenance). The problems are concentrated in three themes: **location lifecycle**
(engines that never stop), **unthrottled high-frequency bridge events**, and **memoization defects
in the hottest JS components**.

## 2. Battery: location tracking

### 2.1 Android — map path never releases the location engine (High, Confirmed)

- The location engine request is hard-coded to the most battery-hungry combination: 1000 ms
  interval, 1000 ms fastest interval, `PRIORITY_HIGH_ACCURACY`, 0 m displacement —
  Android `location/LocationManager.kt:38-48` (constants at `:145-146`). Only `minDisplacement`
  is JS-configurable; there is no way to widen the interval or choose
  `BALANCED_POWER_ACCURACY`.
- `MLRNCamera.removeFromMap` is an empty body (Android `components/camera/MLRNCamera.kt:128`),
  while `enableLocationComponent` registers a persistent listener
  (`MLRNCamera.kt:306`). `LocationManager` is an app-scoped singleton, so once any camera enables
  user tracking, the 1 Hz HIGH_ACCURACY engine runs for the rest of the process lifetime — even
  after the map unmounts.
- The leaked listener does almost nothing useful: it only calls
  `userLocation.setCurrentLocation` (`MLRNCamera.kt:65-78`); camera-follow itself is driven
  natively by `LocationComponent` camera modes. GPS stays on to feed a value nobody reads.
- No pause/background handling on the map path: `LocationComponent.onStart()` is called when
  following (Android `components/location/LocationComponentManager.kt:109`) but `onStop()` is
  never called anywhere; `MLRNMapView.onPause` only sets a flag. The component is handed the
  engine directly (`LocationComponentManager.kt:136`) and keeps consuming updates while
  backgrounded.
- Contrast — the standalone JS location module does this correctly: `onHostPause → disable()`,
  `onHostDestroy → dispose()` (Android `modules/MLRNLocationModule.kt:42-48,127,137`). The fix is
  to give the map path the same symmetry.
- Default render mode is `RenderMode.COMPASS` (`LocationComponentManager.kt:33`), which keeps
  the magnetometer/accelerometer registered via the SDK's compass engine. **Suspected:** those
  sensors keep running in the background because `onStop()` is never called.
- Two independent subscriptions share the engine (the `LocationManager` callback and the
  `LocationComponent`'s own request), and `MLRNLocationModule.disable()` removes only the first —
  disabling the JS module does not stop the map's consumer.

**Fix direction:** implement `MLRNCamera.removeFromMap` (remove listener, disable location when
last consumer leaves), call `LocationComponent.onStop()`/`onStart()` from the map lifecycle, drop
the do-nothing camera listener, and expose interval/priority to JS.

**Fixed (2026-07-24)** — the no-consumer leak. `LocationManager` now creates its engine exactly
once (previously `enable()` re-created the `LocationEngine` per call, leaving the
`LocationComponent` — handed the reference once at `LocationComponentManager.kt:136` —
subscribed through a stale proxy with divergent params; a finding the audit missed) and
refcounts `enable(owner)`/`disable(owner)` across consumers, with `dispose()` removed.
`MLRNCamera.removeFromMap` releases the listener and its hold, plus a new
`MLRNCameraManager.onDropViewInstance` because Fabric subtree teardown (navigation away, dev
reload) never calls `removeFromMap`. `MLRNLocationModule` releases only its own hold, so JS
`stop()` no longer kills the camera path (and vice versa). Deliberately deferred to
`LOCATION-LIFECYCLE-PROPOSAL.md`: `LocationComponent.onStop()` on host pause (background
behavior unchanged — with a tracking camera mounted, host pause now leaves the manager callback
subscribed; the old global stop was an accident of the shared singleton), engine params exposure
to JS, and dropping the do-nothing listener (kept, now unregistered on teardown). Plain-English
writeup: `LOCATION-LIFECYCLE-FIXES.md`.

### 2.2 iOS — max accuracy, heading always on, no lifecycle pause (High, Confirmed)

- `CLLocationManager` is created bare (iOS `modules/location/MLRNLocationManager.m:137-143`):
  no `desiredAccuracy` (so it defaults to `kCLLocationAccuracyBest`), no `activityType`, no
  `pausesLocationUpdatesAutomatically`, no `headingFilter` anywhere in the codebase.
- `start` unconditionally begins both location *and* heading updates
  (`MLRNLocationManager.m:45-46`). When a displacement filter is set, heading *data* is discarded
  (`:110-115`) but `stopUpdatingHeading` is never called independently — the magnetometer keeps
  drawing power.
- Default `distanceFilter` is none (`displacement = 0.0`, `:28`), so every GPS fix produces a
  delegate callback and a bridge event.
- Location is not tied to any view or app lifecycle: no `willMoveToWindow`/background observers
  exist; updates continue while the map is hidden or the app is backgrounded until JS explicitly
  calls `stop`.

**Fix direction:** set a sane `desiredAccuracy` default and expose it to JS (mirroring whatever
Android grows), start heading updates only when a consumer needs heading, and pause on
`UIApplicationDidEnterBackground` unless explicitly configured for background use.

**Partially fixed (2026-07-24)** — heading updates removed entirely rather than made
conditional: the `CLHeading` was stored into a write-only property and never reached JS (the
event's `heading` field is `CLLocation.course` — worse than the audit stated), and with the
default `displacement == 0` every magnetometer callback re-emitted `onUpdate` with a stale
unchanged location; events now fire only on actual fixes. The module retain cycle is also fixed
(§6), which is the real teardown-parity win: modules now deallocate on instance teardown and
`CLLocationManager` actually stops (previously one leaked GPS session per JS reload). Still
open, deferred to `LOCATION-LIFECYCLE-PROPOSAL.md`: `desiredAccuracy` default, `activityType`,
background pause. Plain-English writeup: `LOCATION-LIFECYCLE-FIXES.md`.

### 2.3 JS — global `minDisplacement` clobbering (Med, Confirmed)

`LocationManager.setMinDisplacement` mutates global native state
(JS `modules/location/LocationManager.ts:128-130`) but is set per-consumer in `useCurrentPosition`
(JS `hooks/useCurrentPosition.ts:30-34`). Two simultaneous consumers with different values
last-writer-win, and nothing restores the previous value on unmount — update cadence becomes
non-deterministic in multi-consumer apps.

**Fix direction:** track the minimum requested displacement across active consumers in the
`LocationManager` singleton and apply that.

**Not fixed (2026-07-24)** — deferred to `LOCATION-LIFECYCLE-PROPOSAL.md` (JS `LocationManager`
hardening) alongside the related uncounted-imperative-`start()`/unguarded-`stop()` issues.

## 3. Bridge & event traffic

### 3.1 Per-frame render events always cross the bridge (High, Confirmed)

`onWillStartRenderingFrame` / `onDidFinishRenderingFrame` / `onDidFinishRenderingFrameFully` are
emitted on every rendered frame regardless of whether JS subscribed:

- iOS: the Fabric wiring fires whenever `_eventEmitter` exists — which is always, while mounted
  (iOS `components/map-view/MLRNMapViewComponentView.mm:197-223`; delegate at
  `components/map-view/MLRNMapView.m:790-800`).
- Android: `MLRNMapView.kt:792-819` dispatches the same set per frame. Payloads are empty, so the
  cost is allocation + dispatch, but at 60 fps that is 60+ native→JS dispatches per second per
  map, usually to reach no listener at all.

**Fix direction:** gate emission on whether the JS side registered the handler (Fabric exposes
this via the view props being set), or emit only when a `hasListeners`-style flag is on.

**Fixed (2026-07-23):** Fabric `DirectEventHandler`s are *not* visible to native as props
(the audit's parenthetical was wrong), so a new native prop `handledMapChangedEvents`
carries the subscription: `Map.tsx` derives it from handler presence (memoized on presence
booleans so the array identity is stable across renders), and native gates the three
frame-event dispatches on it — Android in the `onWillStartRenderingFrame` /
`onDidFinishRenderingFrame` overrides (leaving `markerViewManager?.updateMarkers()` and
`handleMapChangedEvent`'s other callers untouched), iOS in the two frame delegate methods
(deny-by-default `nil` set). Listener/block wiring stays unconditional; only the
WritableMap/dispatch resp. emitter call is skipped. Direct native-component consumers
bypassing `Map` would now need to pass the prop — none exist in this fork.

### 3.2 `onRegionIsChanging` — heavy payload per camera tick, no throttle (High, Confirmed)

- Android: `addOnCameraMoveListener` → `handleMapChangedEvent("onRegionIsChanging", true)`
  (`MLRNMapView.kt:541-543`) → `makeViewState` (`:1462-1505`) builds a nested `WritableMap` with
  camera position **and** `projection.visibleRegion.latLngBounds` — a non-trivial projection
  computation — on every camera-move tick of a pan/zoom/animation.
- iOS: `mapViewRegionIsChanging:` → `makeViewState:` (full bounds dictionary) → emit
  (`MLRNMapView.m:756-760`, `:884`), then the component view re-boxes the `NSDictionary`
  field-by-field into `folly::dynamic` per event (`MLRNMapViewComponentView.mm:21-59`).
- Mitigating nuance (Android): `MapChangeEvent` doesn't override coalescing, so RN's default
  same-name coalescing collapses deliveries per frame batch — that bounds JS-side invocations but
  not the per-tick native `makeViewState` cost.

### 3.3 Both platforms' throttle mechanisms are dead code (Med, Confirmed)

- Android: `components/AbstractEventEmitter.kt` implements a 10 ms per-key rate limiter — no class
  extends it and `handleEvent` has zero callers; all live events go straight to
  `eventDispatcher.dispatchEvent`.
- iOS: `components/ViewManager.m:26-47` implements `EVENT_THROTTLE_S` in `fireEvent:` — never
  invoked.
- The offline modules on **both** platforms throttle correctly (~300 ms, and iOS additionally
  checks for an emitter before sending): Android `modules/MLRNOfflineModule.kt` (`shouldSendUpdate`),
  iOS `modules/offline/MLRNOfflineModule.mm:676-690`. This is the pattern the region/frame events
  should adopt.

**Fix direction:** add a native time-based throttle (JS-configurable, like the offline modules) to
`onRegionIsChanging`, and delete the two dead throttle implementations either way.

### 3.4 Per-frame main-thread marker work (Med, Confirmed — Android)

`onWillStartRenderingFrame` also runs `markerViewManager?.updateMarkers()`
(`MLRNMapView.kt:792-793`), which iterates every marker and calls
`projection.toScreenLocation` per marker on the main thread each frame
(`components/annotations/marker/MarkerViewManager.kt:60-70`). Cost scales linearly with marker
count on the hottest path in the wrapper.

## 4. Main-thread work / jank

- **Android — style JSON double-parsed (Med, Confirmed).** Inline styles are first fully parsed
  by `ConvertUtils.isJSONValid` (a complete `JSONObject` parse used only as a validity check,
  `utils/ConvertUtils.kt:158-164`), then parsed again by `Style.Builder().fromJson` — both on the
  UI thread, in two places (`MLRNMapView.kt:504-514`, `:848-859`). A cheap first-character check
  (`{`) would eliminate the first parse entirely.

  **Reviewed (2026-07-24), deliberately not fixed — low priority.** The finding is mis-framed:
  `isJSONValid`'s job is to *discriminate* inline style JSON from a style URL (pick `fromJson`
  vs `fromUri`), not to validate — `fromJson` hands the string to MapLibre Native, which fully
  parses and properly rejects malformed JSON anyway. iOS discriminates the same way, by
  URL-parseability, not JSON validity (iOS `utils/MLRNUtils.m:128-140`). Cost is smaller than
  the entry implies: URL styles pay ~nothing today (`JSONObject` throws on the first token), so
  only inline-JSON apps pay the redundant full parse — per style set, not per frame. The
  stronger argument for the eventual fix is error semantics: inline JSON with a syntax error
  fails the pre-parse and is silently routed to `fromUri`, producing a nonsensical URL-load
  failure instead of a style-parse error. When fixed, replace `isJSONValid` with a
  `trimStart().startsWith("{")` discriminator — sound because a style document is always a JSON
  object and no URI starts with `{`; the "first char can't prove validity" objection doesn't
  apply since nothing needs validity. Correction: three call sites, not two — the audit missed
  `modules/MLRNStaticMapModule.kt:89`. Style-URL apps (VeloPlanner) are unaffected.
- **Android — synchronous `queryRenderedFeatures` on the main thread (Med, Confirmed).**
  `MLRNMapView.kt:706,1109,1143` — self-documented ANR risk (`:667-675`); this branch already
  guards the paused/detached cases, but the happy path still blocks the UI thread on the render
  thread.
- **Android — annotation bitmaps rasterized on the UI thread (Low, Confirmed).** Every layout
  change of a `PointAnnotation` child re-renders the view to an ARGB_8888 bitmap synchronously
  (`components/annotations/pointannotation/MLRNPointAnnotation.kt:165-205`,
  `utils/BitmapUtils.java:92-105`).
- **Android — serialized image downloads (Low, Confirmed).** `DownloadMapImageTask` correctly does
  I/O in `doInBackground`, but is launched with `task.execute(...)`
  (`components/images/MLRNImages.kt:116,129`) → `AsyncTask.SERIAL_EXECUTOR`, one image at a time
  process-wide, plus an extra `bitmap.copy(ARGB_8888)` per image. `AsyncTask` is also deprecated.
- **iOS — synchronous GeoJSON parse on the main thread (Med, Confirmed).**
  `MLNShape shapeWithData:` runs synchronously during prop updates
  (`utils/MLRNUtils.m:37`, called from `components/sources/MLRNGeoJSONSource.m`). Large
  FeatureCollections parse on the main thread on every data update.
- **iOS — first-use style file write on the main thread (Low, Confirmed).** Inline style JSON is
  written to disk synchronously during the prop update (`MLRNUtils.m:146-191`); md5-cached, so
  only the first use of a given style pays it.
- **iOS — snapshot encode on the main thread (Low, Confirmed).** `takeSnap:` forces a synchronous
  render then PNG-encodes + base64s on the same thread (`MLRNMapView.m:552-559`,
  `utils/MLRNImageUtils.m:5-22`). On-demand only.
- **Good pattern already present:** iOS style-image loading is off-main with only the final
  `setImage:forName:` hopped back (`components/images/MLRNImageQueueOperation.m:114-145`).

## 5. React/JS layer performance

### 5.1 Ineffective `useMemo` — dependency is a fresh object every render (High, Confirmed)

- `components/layer/Layer.tsx:220-269`: the component destructures `({ id, ...props })` and then
  memoizes on `[props]` — a rest object with a new identity every render, so the memo **never**
  hits. Every parent re-render re-runs `mergeStyleProps` + `transformStyle` (which walks every
  style key through `processColor` / `Image.resolveAssetSource` / `BridgeValue`,
  `utils/StyleValue.ts:16-52`). `Layer` is the most-instantiated component in the library and is
  not wrapped in `memo` either.
- `components/map/Map.tsx:662-675`: same pattern — `useMemo(..., [props])` on a rest object, so
  `JSON.stringify(mapStyle)` and the light transform re-run on every re-render. `Map` is
  `memo`-wrapped, which reduces how often it re-renders but the internal memo is still dead
  weight.

**Fix direction:** memoize on the actual inputs (`paint`, `layout`, `style`, `filter`,
`mapStyle`, `light`, …) instead of the rest object, and wrap `Layer` in `memo`.

**Fixed (2026-07-23):** `Layer` and `Map` memoize the expensive transforms on
*serialized* keys of the style inputs (`JSON.stringify([paint, layout, style])` etc.)
rather than references — consumers commonly pass inline style literals, so
reference-keyed deps would still miss every render. The stable `reactStyle`/`filter`
identities also stop per-render native prop resends. `Layer` is deliberately not
wrapped in `memo` (shallow compare can't hit with inline literals; the per-field
memos carry the win). Validated in VeloPlanner via a temporary pnpm patch: recomputes
now fire only on genuine value changes (e.g. selection toggling `line-opacity`).

### 5.2 `GeoJSONSource` re-stringifies on every render (High, Confirmed)

`components/sources/geojson-source/GeoJSONSource.tsx:235` runs
`JSON.stringify(data)` inline in render with no `useMemo`. The component is `memo`-wrapped, but
with an inline `data` object (the common case) the shallow compare fails every time. It compounds
badly with animation: `UserLocation` defaults `animated=true`, coordinate animation is JS-driven
(`useNativeDriver: false` throughout `utils/animated/`), so the animated source re-renders — and
re-stringifies the entire FeatureCollection — **per animation frame**. Cost scales with data size.

**Fix direction:** `useMemo(() => typeof data === "string" ? data : JSON.stringify(data), [data])`.
Worth noting in docs that GeoJSON animation is inherently JS-thread work (a serialized `data`
string prop can't use the native driver), so its per-frame cost is proportional to geometry size.

**Fixed (2026-07-23):** exactly the fix direction above. Validated in VeloPlanner via a
temporary pnpm patch: a 9.7 MB FeatureCollection that previously re-stringified three
times on mount (~175 ms each, blocking the JS thread) now serializes once per actual
data change. The animation caveat stands — animated sources produce a new `data` object
per frame, so their per-frame stringify remains, proportional to geometry size.

### 5.3 Minor render-identity churn (Low, Confirmed)

`components/annotations/view-annotation/ViewAnnotation.tsx:180-234`: `nativeAnchor`,
`nativeOffset`, and `style={[props.style, styles.container]}` all get new identities each render
and the component isn't memoized — the native prop diff sees `style` as changed every render,
multiplied across annotations.

Also: `modules/location/LocationManager.ts:70` ships a raw `console.log` on the error path; the
rest of the library routes through `LogManager`.

## 6. Memory & lifecycle

- **iOS — retain cycle in the location module (Med, Confirmed → Fixed 2026-07-24).**
  `modules/location/MLRNLocationManager.h:9` declares the delegate property `strong`; the module
  strongly owns the manager and sets itself as delegate → module ↔ manager cycle. Long-lived
  TurboModule today, but it would keep the `CLLocationManager` alive through any teardown. Make
  the delegate `weak`. **Fixed:** delegate is now `weak`, and `dealloc` was rewritten in the same
  commit — it becomes reachable for the first time once the cycle breaks, and its old body
  dispatched a block strongly capturing `self` mid-dealloc (over-release/UB). In practice the
  cycle leaked one module+manager pair with live GPS per JS reload.
- **Android — `MarkerViewManager.onDestroy()` never called (Low, Confirmed).** Defined at
  `MarkerViewManager.kt:136` but `MLRNMapView.dispose()` never invokes it; marker view references
  aren't proactively cleared on teardown.
- **Android — annotation style images not removed (Low, Suspected).**
  `MLRNPointAnnotation.removeFromMap` deletes the symbol but not the style images added for
  child/callout bitmaps; they may linger in the style.
- **iOS — no explicit MapView teardown (Low, Confirmed, likely acceptable).** No
  `dealloc`/`willMoveToWindow`; `RCTInvalidating` only detaches React subviews. Fabric recycling
  is disabled (`shouldBeRecycled = NO`), so every remount pays full re-init — deliberate
  (avoids stale state) but worth knowing.
- **Process-lifetime singletons (Low, Confirmed).** iOS `MLRNTransformRequest` permanently
  installs itself as the `MLNNetworkConfiguration` delegate; `MLRNLogging` installs a global
  handler where the last of multiple maps wins and it is never cleared.
- **Bounded statics (fine):** Android `BitmapUtils` 1 MB LRU bitmap cache and the shared
  placeholder bitmap; `LocationManager` singleton holds only a `WeakReference` on the app context.

## 8. Prioritized roadmap

1. **Map-path location lifecycle** — implement `MLRNCamera.removeFromMap`, wire
   `LocationComponent.onStop()` into the map lifecycle, remove the do-nothing camera listener;
   set iOS `desiredAccuracy` default and conditional heading. Biggest battery win, small diffs.
   — **Done 2026-07-24** for the never-released-engine core (see §2.1/§2.2/§6: Android owner
   refcounting + camera teardown, iOS heading removal + retain cycle). Background pause, iOS
   accuracy default, and JS-exposed engine params deliberately deferred —
   `LOCATION-LIFECYCLE-PROPOSAL.md` is the issue-ready writeup.
2. **Event gating/throttling** — gate per-frame render events on an actual JS subscriber
   (**done 2026-07-23**, see §3.1); add a native throttle to `onRegionIsChanging` (reuse the
   offline modules' pattern). Delete both dead throttle implementations.
3. **JS memoization fixes** — `Layer`, `Map`, `GeoJSONSource` (three small, low-risk diffs with
   outsized effect for data-heavy apps). — **Done 2026-07-23** (see §5.1/§5.2).
4. **Main-thread relief** — drop the redundant `isJSONValid` pre-parse (reviewed 2026-07-24, see
   §4 — reframed as a discrimination/error-semantics fix, low priority); move GeoJSON parsing off
   the main thread on iOS; replace `AsyncTask.SERIAL_EXECUTOR` for image downloads.
5. **Dead-code sweep** — table in §7.1; purely mechanical.
6. **Test backfill + guardrails** — cover the untested components; consider a coverage threshold
   and a shared-type check for the duplicated codegen blocks.
